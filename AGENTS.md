# AGENTS.md

## Назначение проекта

FLEXX — **mobile-first e-commerce приложение**: каталог, категории, карточки товаров, корзина, оформление заказа без регистрации и административная панель. Это действующее приложение с данными и бизнес-правилами, а не шаблон лендинга.

Расширяйте проект небольшими понятными изменениями. Приоритет — простота, читаемость для новых участников команды, доступность и удобство покупки с телефона. Сохраняйте существующие сценарии и данные.

## Структура проекта

```text
src/
  app/
    _components/                # компоненты корневого layout
    (site)/
      _components/              # общие компоненты витрины
      catalog/_components/      # компоненты каталога
      cart/
      product/[slug]/
      order/[publicId]/thanks/
    (panel)/
      auth/
      panel/
        _components/            # общие компоненты панели
        categories/
        products/
        orders/
    globals.css
    layout.tsx
  entities/
    admin/
      lib/                      # токены и лимитер входа
      services/                 # учётные данные, сессии, вход/выход
    category/
    product/
      repository/               # только взаимодействие с БД
      services/                 # серверная и бизнес-логика
      ui/                       # UI сущности, общий для разделов
      domain.ts                 # типы и схемы
      catalog-params.ts
    order/                      # domain, repository, services, status
  features/
    cart/                       # store, hydration, UI, checkout, тесты
  shared/
    ui/                         # универсальные UI-примитивы
    components/                 # компоненты без привязки к разделу
    hooks/
    lib/
  prisma/                       # контракт, клиент, Composer, seed
  proxy.ts
scripts/                        # служебные команды и общие тесты
public/                         # статические ресурсы и service worker
```

У `category` и `order` те же границы `repository` / `services`, что у `product`. Не создавайте пустые слои для симметрии. Учётные данные администратора читаются из окружения, поэтому репозиторий БД для них не нужен.

Имена обычных файлов и папок — `kebab-case`; компоненты — `PascalCase`, функции — `camelCase`. Сохраняйте специальные имена файлов Next.js. Между разделами используйте существующий alias `@/src/...`; короткие относительные импорты внутри модуля допустимы. Не создавайте barrel-файлы только для сокращения пути.

## Основные принципы

- **KISS:** прямые функции и композиция компонентов предпочтительнее классов, фабрик, контейнеров зависимостей и многоступенчатых обёрток.
- **DRY:** одно бизнес-правило должно иметь одно место определения. Объединяйте повторяющуюся логику, но не связывайте независимые сценарии только из-за похожего JSX.
- **YAGNI:** не добавляйте абстракции, зависимости, настройки, слои, универсальные репозитории и возможности «на будущее».
- Основной поток: **страница / компонент → services → repository → БД**. UI не импортирует репозитории, сервисы не импортируют клиент БД.
- **Repository:** только запросы, проекции, сортировка, запись и предоставление операций транзакции. Никаких `requireAdmin`, Zod-валидации, бизнес-ошибок, `console`, обработки форм или обновления кеша.
- **Services:** проверка прав, валидация входа, бизнес-правила, координация репозиториев, обработка ошибок и логирование. Обновление кеша инициирует сервис через существующий helper.
- **Отдельные папки `actions` запрещены.** Вызываемые клиентом серверные функции размещайте в `services` с `"use server"`. Этот модуль экспортирует только подходящие асинхронные серверные функции; внутреннюю логику и типы размещайте отдельно.
- Чистые схемы, типы и расчёты остаются в `domain.ts` или небольших тематических модулях без зависимости от UI/БД. Не добавляйте второй набор типов для уже описанной схемы без причины.
- При необходимости преобразуйте результат репозитория в DTO в сервисе; передавайте клиенту только необходимые сериализуемые данные.
- Для транзакционных сценариев следуйте примеру `order/services/create-order.ts`: сервис выполняет бизнес-алгоритм внутри `withOrderTransaction`, репозиторий предоставляет операции. Не разрывайте атомарность заказа и остатков.
- Ожидаемые ошибки возвращайте в существующем формате состояния формы/операции. Неожиданные ошибки логируйте с контекстом на сервере, не раскрывая секреты и персональные данные. Не маскируйте сбой пустым списком или успешным ответом.
- Не перехватывайте `redirect()` и `notFound()` общим обработчиком ошибок. Ошибка обновления кеша после успешной записи не должна сообщать, что запись не состоялась.

## Layout и секции

- `page.tsx` собирает сценарий и получает данные через сервисы; `layout.tsx` задаёт общую оболочку. Не размещайте запросы к БД и бизнес-валидацию в JSX.
- Серверные компоненты — исходный выбор. Добавляйте `"use client"` только там, где нужны состояние, события, эффекты или API браузера.
- Сохраняйте небольшие клиентские границы: серверная карточка товара + клиентская кнопка корзины, а не клиентская страница целиком.
- Не вызывайте из серверного компонента функцию, экспортированную клиентским модулем. Например, используйте `LinkButton`, а не вызов клиентского `buttonVariants()` на сервере.
- Провайдеры размещайте настолько близко к потребителю, насколько возможно. Восстановление корзины относится к витрине, а не к панели.
- Компонент одного маршрута храните рядом с ним; общий для раздела — в его `_components`; UI сущности — в `entities/<entity>/ui`; универсальный примитив — в `shared/ui`.
- Используйте существующий ритм отступов и ширину соседних страниц. Не вводите общий `Container` / `Section`, если он лишь добавляет лишний уровень JSX.
- Для переходов используйте `next/link` и существующие обёртки ссылок, для действий — кнопки. Не превращайте `div` в ссылку через `onClick`.
- Сохраняйте осмысленные `loading.tsx`, `error.tsx`, пустые состояния и metadata. Не дублируйте один серверный запрос в странице и metadata без необходимости; следуйте существующему использованию React `cache` в сервисах.

## Дизайн-система (КРИТИЧНО ВАЖНО)

**Перед созданием любого нового UI-компонента или визуальным изменением прочитайте корневой `DESIGN.md`.** Компоненты, состояния, типографика, цвета и адаптивность должны соответствовать ему.

На момент создания этих правил `DESIGN.md` отсутствует. Если файл по-прежнему не создан, сообщите об этом и согласуйте недостающие дизайн-решения; продолжайте независимую работу с логикой. Не выдавайте собственные предположения за требования DESIGN.md. При явно разрешённом пользователем продолжении опирайтесь на существующие компоненты и токены.

Реализация общих стилей находится в **`src/app/globals.css`** (именно `globals.css`, не новый `global.css`). Не создавайте параллельную дизайн-систему. Если DESIGN.md расходится с реализацией, явно укажите расхождение и решайте его в рамках задачи.

Не придумывайте новые цвета, шрифты, тени и градиенты для каждого компонента. Используйте семантические токены `background`, `foreground`, `primary`, `muted`, `border`, `destructive` и существующие варианты UI.

## Tailwind CSS

- Все стили находятся в `src/app/globals.css` либо непосредственно в компоненте через Tailwind в `className`. Не добавляйте CSS Modules, отдельные стили компонентов, CSS-in-JS, styled-components или второй глобальный stylesheet.
- Tailwind 4 уже подключён в `globals.css` через `@import "tailwindcss"`; там же подключены `tw-animate-css` и `shadcn/tailwind.css`. Не дублируйте подключение.
- Общие токены находятся в CSS-переменных и `@theme inline`, базовые правила — в `@layer base`. Добавляйте общий CSS только для повторяющейся потребности или оформления, которое неудобно выразить утилитами.
- Локальную раскладку, отступы и адаптивность задавайте Tailwind-классами в JSX. Используйте шкалу размеров, `gap-*`, `size-*` для равных сторон и семантические цвета.
- Для общих UI-компонентов сначала используйте `variant` и `size`; не переопределяйте их оформление произвольными цветами на каждом месте вызова.
- Условные классы объединяйте через существующий `cn`. Не дублируйте токены hex-значениями и длинные наборы вариантов вручную.
- Динамические классы должны оставаться обнаруживаемыми Tailwind: используйте полные строки вариантов, а не `bg-${color}-500`.
- Наличие `.dark` токенов не означает готовую функцию переключения темы. Не возвращайте `next-themes` без задачи на тему.
- Не переносите синтаксис Tailwind старых версий по памяти: сверяйте установленную версию, конфигурацию и официальную документацию при сомнениях.

## Контент и заглушки

- Товары, цены, остатки, категории и заказы поступают из БД через сервисы. Не добавляйте параллельные массивы моковых товаров в `shared` или компоненты.
- Демоданные допустимы в seed, а фикстуры — в тестах. Не подменяйте ими данные при ошибке сервера.
- Пишите пользовательские сообщения на русском; используйте понятные сообщения об ошибках и пустых результатах. Не показывайте технические детали Prisma, стеки и внутренние идентификаторы ошибок.
- Сохраняйте точность цен; используйте общий formatter, не округляйте отображение до рублей без требования.
- `ARCHITECTURE_REVIEW.md` — исторический аудит до рефакторинга. Не восстанавливайте удалённые слои и файлы на основании его старой инвентаризации.

## Компоненты

- Сначала проверьте `src/shared/ui`, UI сущности и `_components` нужного раздела. Компонуйте готовые примитивы вместо повторной реализации кнопки, диалога, таблицы или поля.
- Следуйте локальному React Aria API: например, `onPress`, `isDisabled`, `render` там, где это поддерживает конкретная обёртка. Не используйте `asChild` или другие props по аналогии с чужим пресетом.
- Не перезаписывайте существующие shadcn-компоненты генератором без просмотра различий и сохранения локальных изменений.
- Используйте `Field`, `FieldGroup`, `FieldLabel`, `Input`, `Textarea` и существующие компоненты ошибок в формах. Диалоги должны иметь доступное название.
- Разделяйте компоненты по ответственности, а не по произвольному лимиту строк. Пример: контейнер корзины, строка товара, форма оформления.
- Локальное состояние — React; корзина — существующий Zustand store; параметры каталога — URL. Не создавайте второй источник истины для фильтров и не дублируйте parser из `catalog-params.ts`.
- В административных списках переиспользуйте общую таблицу. Переход к серверной пагинации делайте по реальной потребности и измерениям.
- Анимации применяйте умеренно; они не должны мешать выбору товара, вводу данных или оформлению заказа.

## Форма и деплой

- Используйте текущие паттерны React: `useActionState` для серверных форм там, где он уже применяется, и контролируемую форму оформления с вызовом сервиса. React Hook Form в проекте не установлен; не добавляйте его для простой формы.
- Валидируйте все клиентские данные на сервере через Zod, включая идентификаторы. Клиентская проверка дополняет серверную, но не заменяет её.
- В каждом сервисе панели вызывайте `requireAdmin()` до обращения к данным. Проверки Proxy и layout сами по себе недостаточны.
- Цена, итог заказа, доступность и остаток берутся с сервера. Сохраняйте транзакцию, порядок резервирования по ID, проверку изменившихся цены/остатка и снимки названия/цены в заказе.
- Предотвращайте повторную отправку формы и показывайте состояние ожидания. Очищайте корзину только после успешного создания заказа.
- Секреты хранятся в серверном окружении; `.env.example` содержит только безопасные примеры. Не используйте `NEXT_PUBLIC_` для подключения к БД и административных секретов.
- Сохраняйте оба режима: `npm run dev` с `DATABASE_URL` и `npm run dev:composer` с привязкой Composer. Не скрывайте сбои Composer безусловным fallback.
- Контракт БД — `src/prisma/contract.prisma`. Генерируйте `contract.json` / `contract.d.ts` через `npm run contract:emit`, не редактируйте их вручную. Генерация не заменяет миграцию БД.
- Миграции проверяйте на отдельной базе. `db:reset` удаляет данные; не используйте его как исправление ошибки запуска. Seed добавляет отсутствующие демозаписи, не удаляет и не перезаписывает существующие.
- Не запускайте деплой или изменения рабочей БД как часть обычной проверки кода, если это не входит в запрос пользователя.
- PWA: сохраняйте исключения для панели, авторизации, API, персональных ответов и RSC/prefetch. Не выдавайте кеш главной страницы вместо другого URL и не кешируйте отправку заказа.

## Проверка изменений

Для изменений кода запускайте:

```bash
npm run check
npm run build
npm run format:check
```

`check` включает ESLint, TypeScript и тесты. `build` автоматически запускает генерацию контракта. Для изменения только документации достаточно проверки форматирования и корректности путей/команд; сборка не нужна.

При изменениях интерфейса запускайте `npm run dev` и проверяйте затронутые сценарии в браузере. Используйте **next-devtools MCP**, когда он доступен: инициализация инструмента, обнаружение сервера, проверка runtime-ошибок и релевантная документация Next.js. Если инструмент недоступен, сообщите об этом и используйте логи и официальную документацию; не утверждайте, что проверка MCP выполнена.

Тесты размещайте рядом с логикой в `*.test.ts`; общие проверки находятся в `scripts`. Тестируйте поведение и риски: права, валидацию, деньги, остатки, корзину, URL и кеш. Не удаляйте проверку, чтобы скрыть регрессию. Не создавайте тесты, которые лишь копируют реализацию.

Архитектурный тест `scripts/architecture.test.mjs` защищает границы слоёв. Сохраняйте его при расширении проекта. Подставной репозиторий в тесте заказа не заменяет проверку транзакций и конкурентных запросов на PostgreSQL.

Перед завершением проверьте diff, неиспользуемые импорты и старые пути после переносов. Укажите выполненные проверки и оставшиеся ограничения; не заявляйте о проверках, которые не запускались.
