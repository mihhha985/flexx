# FLEXX — интернет-магазин обуви

Next.js 16 (App Router), React 19, Prisma 8 RC / PostgreSQL, React Aria / shadcn, Zustand.

## Запуск

1. Установите зависимости: `npm ci`.
2. Скопируйте `.env.example` в `.env` и заполните подключение PostgreSQL и настройки администратора.
3. Сгенерируйте клиент: `npm run contract:emit`.
4. Запустите `npm run dev`. В прямом режиме необходим `DATABASE_URL`.

Альтернативный запуск через Prisma Composer: `npm run dev:composer`. Конфигурация находится в `module.ts`, `service.ts` и `src/prisma/composer.ts`. Ошибки Composer не маскируются переключением на другое подключение: fallback допускается только при отсутствии привязки в прямом режиме.

`npm run build` автоматически обновляет контракт перед сборкой. `npm start` запускает готовую сборку. `npm run deploy` собирает и развёртывает приложение через Composer.

## Подготовка к production

1. Используйте Node.js 22.12 или новее (требование Puppeteer) и устанавливайте зависимости через `npm ci`.
2. Задайте все переменные из `.env.example`. Для рабочего окружения обязательны надёжные
   `ADMIN_PASSWORD` и `ADMIN_SESSION_SECRET`, а для загрузки изображений — действующие параметры
   S3-совместимого хранилища. Укажите публичный адрес магазина в `SITE_URL`, иначе canonical,
   Open Graph, `robots.txt` и `sitemap.xml` будут ссылаться на localhost. Для PostgreSQL через TLS явно используйте
   `sslmode=verify-full` в `DATABASE_URL`, если провайдер не требует иной режим.
3. Проверьте миграции на отдельной базе и просмотрите план перед применением. Не запускайте
   `db:reset` на рабочей базе.
4. Выполните `npm run check`, `npm run format:check` и `npm run build`.
5. Для Composer задайте `PRISMA_SERVICE_TOKEN` и `PRISMA_WORKSPACE_ID`, затем выполните
   `npm run composer:deploy`. Команда `npm run deploy` предварительно запускает production-сборку.

Перед публикацией замените демонстрационные контактные данные на реальные и проверьте условия
доставки, оплаты и возврата. Приложение не применяет миграции к рабочей базе во время обычной
проверки кода.

## Как устроен код

Поток данных: **страница / компонент → services → repository → БД**.

- `src/app` — маршруты Next.js, layouts, loading/error и сборка страниц. `(site)` — витрина, `(panel)` — вход и панель. Папки `_components` содержат компоненты только соответствующего раздела.
- `src/entities/{product,category,order}` — модели предметной области, схемы валидации, серверная логика и запросы.
- `repository` — только запросы к БД и операции транзакции. Здесь нет проверки прав, обработки бизнес-ошибок и логирования.
- `services` — серверные функции: проверка прав, валидация входа, бизнес-правила, обработка ошибок, логирование и обновление кеша. Отдельного слоя `actions` нет. Файлы с `"use server"` доступны клиентским компонентам; внутренние серверные модули используют `server-only`.
- `src/entities/admin` — авторизация. Учётные данные поступают из окружения через сервис, поэтому репозиторий для них не нужен.
- `src/features/cart` — корзина, её хранилище, восстановление состояния, строки товаров и форма заказа.
- `src/shared` — универсальный UI и небольшие общие функции. Компоненты конкретных страниц сюда не добавляем.
- `src/prisma` — контракт, клиент БД и seed. Сгенерированные файлы не редактируем вручную.

Файлы именуем в `kebab-case`. Новый код размещаем рядом с местом использования. Выносим общий модуль, когда уже есть повторение одного правила; похожий JSX сам по себе не требует универсального компонента.

## Основные сценарии

Каталог нормализует поиск, сортировку и страницу в `entities/product/catalog-params.ts`. Слишком большая страница перенаправляет на последнюю с сохранением фильтров. Сортировка имеет дополнительный ключ `id`, чтобы порядок был устойчивым.

Создание заказа валидирует запрос в сервисе, затем выполняет бизнес-проверки и запись внутри одной транзакции. Репозиторий предоставляет операции чтения, резервирования остатков и записи. Цена и остаток проверяются при резервировании; сумма рассчитывается из цен БД, а не из браузера. Денежные вычисления выполняются в копейках, текущий тип хранения в БД сохранён.

Корзина хранится в браузере и восстанавливается только на витрине. Карточка товара серверная; добавление в корзину — отдельный клиентский компонент.

## Администратор

Вход: `/auth`. Панель: `/panel/orders`, `/panel/products`, `/panel/categories`.

В окружении задайте `ADMIN_LOGIN`, `ADMIN_PASSWORD` и случайный `ADMIN_SESSION_SECRET` длиной от 32 символов (например, `openssl rand -hex 32`). Не используйте `NEXT_PUBLIC_` для секретов. После изменения перезапустите приложение.

Каждый сервис панели вызывает `requireAdmin()` до доступа к данным. Проверка в `src/proxy.ts` и layout дополняет, но не заменяет эту защиту. Сессия действует 8 часов; cookie HttpOnly, SameSite=Lax, в production Secure. Изменение учётных данных аннулирует старые сессии.

Лимитер входа хранится в памяти процесса: 10 попыток за 5 минут. Для нескольких экземпляров потребуется общее хранилище лимитов. Панель и авторизация исключены из кеша PWA.

Административные таблицы пока загружают списки целиком и обрабатывают поиск и страницы в браузере. Общая таблица находится в `src/app/(panel)/panel/_components/data-table.tsx`. Переносить пагинацию на сервер стоит по измерениям объёма данных.

## База данных

См. [работу с Prisma](prisma-next.md). `npm run seed` добавляет отсутствующие демонстрационные категории и товары по slug. Существующие записи и заказы не удаляются и не перезаписываются. Запускайте seed осознанно: это запись демонстрационных данных.

`db:reset` — разрушительный сброс БД, не команда обычного запуска. Изменения схемы и миграции проверяем на отдельной базе перед применением к рабочей.

## Импорт товара Amazing Red

Сначала установите зависимости (`npm ci`) и заполните `.env`: `DATABASE_URL` и настройки
Джино `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_PREFIX`, `S3_ACCESS_KEY_ID`,
`S3_SECRET_ACCESS_KEY`, `S3_PUBLIC_BASE_URL`. Бакет должен разрешать публичное чтение
изображений по `S3_PUBLIC_BASE_URL`. Если Chrome ещё не установлен,
выполните `npx puppeteer browsers install chrome`.

Просмотр данных без записи в БД и загрузки в бакет:

```bash
npm run import:amazing-red -- --url "https://amazingred.ru/d/krossovki-puma-fade-nitro-ls-black-40620305/" --dry-run
```

Импорт товара и фотографий в Джино:

```bash
npm run import:amazing-red -- --url "https://amazingred.ru/d/krossovki-puma-fade-nitro-ls-black-40620305/"
```

Без `--url` используется эта же ссылка. Передавайте обычный URL; скопированная Markdown-ссылка
`[название](URL)` тоже поддерживается. Поддерживаются карточки Amazing Red с такой же
разметкой, включая буквенно-цифровые артикулы. Для black/white/grey/beige/brown HEX задан
в таблице; для неизвестного цвета используется белый `#FFFFFF`. Название со страницы
и slug цвета из ссылки сохраняются, чтобы разные цвета не объединялись в один вариант.
Если цвет повторяется у разных артикулов, к slug каждого такого варианта добавляется
артикул (например, `black-39077601` и `black-39077621`). Оба варианта сохраняются со своими
фотографиями и ценами; уникальные цвета сохраняют прежний slug.
Скрипт собирает все ссылки цветов и исключает повторяющиеся артикулы. Из полученного списка
случайно выбираются **до трёх** вариантов: если уникальных артикулов один или два,
импортируются все имеющиеся; без списка цветов — текущая карточка. Разные артикулы могут
иметь одинаковое название цвета. Каждый запуск, включая `--dry-run`, выбирает набор заново;
первый выбранный вариант становится основным.

Например, New Balance с двумя цветами:

```bash
npm run import:amazing-red -- --url "https://amazingred.ru/d/krossovki-new-balance-204l-beige-u204l2sz/" --category new-balance
```

`npm run import:amazing-red` сохраняет товар и до трёх записей `ProductVariant` одной транзакцией.
Подключение берётся из `.env` через существующий клиент Prisma. Категория `puma` должна
существовать; другую можно указать через `--category <slug>`. Совпадение slug останавливает
импорт без изменения существующего товара.

Название берётся из `h1.product-specs__title`, описание — текст первого `.tab__description`,
страна — `германия`. Slug: первые 20 символов имени страницы без домена и `/d/`, с удалением
конечного дефиса для совместимости с валидацией каталога (`krossovki-puma-fade`).
Ссылки `.product-specs__colors .all-colors__item` образуют полный список для случайного выбора.
Цена и название цвета читаются на странице каждого варианта; HEX задаётся таблицей цветов
в скрипте. Из галереи каждого цвета берутся до 10 уникальных фотографий
в порядке страницы, без дублей слайдера. Они загружаются существующим S3-сервисом в
`S3_PREFIX/products/`; первая фотография становится `avatar`, весь набор — `images`.
В БД сохраняются публичные ссылки Джино. Перед записью проверяется доступность файлов.
При ошибке импорта загруженные этим запуском файлы удаляются; существующие файлы не затрагиваются.
Размеры и остатки не создаются: добавьте их в панели перед продажей.
При неполных данных запись отменяется. Повторный запуск для существующего slug прекращается
до загрузки фотографий и ничего не перезаписывает.

## Проверки

- `npm run check` — ESLint, TypeScript и тесты.
- `npm run build` — production-сборка.
- `npm run format` / `npm run format:check` — единый стиль Prettier.

Тесты покрывают авторизацию, корзину, валидацию, параметры каталога, создание заказа, кеш PWA и архитектурные границы. Последняя проверка запрещает доступ UI к репозиториям, импорт БД вне репозиториев/инфраструктуры и появление папок `actions`.

Тест создания заказа проверяет бизнес-правила на подставном репозитории. Он не заменяет интеграционную проверку конкурентных заказов на PostgreSQL.

Ориентиры Next.js: [структура проекта](https://nextjs.org/docs/app/getting-started/project-structure), [серверные и клиентские компоненты](https://nextjs.org/docs/app/getting-started/server-and-client-components), [изменение данных](https://nextjs.org/docs/app/getting-started/updating-data), [авторизация](https://nextjs.org/docs/app/guides/authentication).
